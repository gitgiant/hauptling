Hauptling delegates coding tasks to Claude, Codex and agy (Antigravity CLI) agents running in disposable containers, across any repo.

## Shape

- **/delegator is a skill** (`SKILL.md` installed user-level in `~/.agents/skills/` and `~/.claude/skills/` by `hauptling setup`), launched in Claude, Codex or agy. The agent in that CLI is the delegator and does the thinking: split, pick models, read reports.
- **`hauptling` Node CLI** is its toolbelt for everything mechanical: spawn, mailbox, status, test jobs, GPU lease, handoff, containers.
- **All state lives in the host store** (SQLite at `~/.hauptling/hauptling.db`, owned only by the host broker), never in a chat. Any delegator can `hauptling resume`.
- **Several delegators at once** (2026-11-25): each session passes `--delegator <id>` on every delegator command (`spawn`, `wait`, `status`, `handoff`, `resume`); CLI env doesn't survive between an agent's shell calls, so it is a flag. Without the flag a command uses the one active delegator, and is refused when several are active (the error lists them). `hauptling delegator end [--delegator ID]` marks one ended (refused while it has live agents); the skill ends its delegator when the goal is done. `resume` without an id, with several active, lists them so the session picks by repo or asks the user.
- **A new session resumes only its own repo** (2026-11-25): `/delegator` first settles the repo (the one the user names, else the current directory's git repo, confirmed with the user), then runs `hauptling resume --repo <repo>`. That continues the active delegator for that repo (a local path also matches the GitHub `owner/name` of its `origin`), or reports none so the session starts a new one. It never picks up another repo's delegator.
- Separate repo, used across repos. New `/delegator` offers: existing GitHub repo, create a new one, or local only.

## Topology

- **Everything runs on one Linux host**: Ubuntu, or WSL on Windows (Windows is treated exactly like an Ubuntu host). Delegator CLI there, never in auto mode.
- **Workers run in Docker containers**: a fresh container per task from the golden image, removed when the task ends (phase 2; phase 1 used local Linux users).
- **Max 3 concurrent agents** per delegator by default.
- No revert step: every task starts from the image. The task's clone lives on the host (`~/.hauptling/work/<agent>`) until cleanup.

## Mailbox

- Code **moves from nullpunkt** (`scripts/mailbox.mjs`, `scripts/coagent/*`, `docs/coagent-mailbox.md`) **into hauptling**; nullpunkt depends on it.
- Store stays per machine. The **host broker** serves the CLI on 127.0.0.1 and containers through the egress proxy's relay.
- Add the `agy` family alongside `claude` and `codex`. One machine-wide mailbox; repo is a status field.
- **One wake path for all vendors**: hooks deliver mail while an agent works; `tmux send-keys` wakes it when idle. The Claude MCP dev channel and `codex queue` are dropped.
- nullpunkt drops `scripts/mailbox.mjs` and `scripts/coagent/`; its docs call `hauptling mail` directly.

## Workers

- **Interactive TUI inside tmux** in the container, so you can attach (`docker exec -it … tmux attach`). Status comes from hooks (all three CLIs have SessionStart, PostToolUse, Stop). **Workers run only Hauptling's hooks** (2026-11-25): the image bakes them in as managed config, Claude `/etc/claude-code/managed-settings.json` with `allowManagedHooksOnly` (status line too) and Codex `/etc/codex/hooks.json` plus `allow_managed_hooks_only` in `/etc/codex/requirements.toml`, so a repo's own `.claude`/`.codex` hooks (its own mailbox, host paths) never run in a worker. Codex no longer gets `--dangerously-bypass-hook-trust`: managed hooks need no trust review. The repo's permissions, CLAUDE.md/AGENTS.md and skills still apply.
- Auto mode on in the container (default).
- **Blocked agents ask you directly**: `hauptling ask "q" --choice A --choice B` sets status `blocked: <question>` and notifies you (a Windows toast on WSL, `notify-send` elsewhere) with up to 4 choice buttons plus "Other…". Buttons open the broker's local answer page (nonce-keyed, has a free-text box). The dashboard blinks; `hauptling reply` and `hauptling attach` also work. The delegator only gets the 300-char final report.
- **No tester agent.** The implementer writes and fixes its own tests; deterministic test jobs run them. Opt-in `--test-writer` per task adds a spec-based test writer for settled areas (protocol, save format, invariants).
- Delegator decides whether a task gets `--test-writer`; you can override.

## Models

- Editable **`models.json`** per vendor: cheapest and rule-of-thumb modes read it directly; suggest mode (default) reasons over it.
- **Round robin rotates the vendor** (claude, codex, agy, claude...); the mode picks that vendor's model.

## Tests and GPU

- `hauptling test request --sha --selector [--gpu] [--artifacts] [--timeout]` returns `req_id`.
- `hauptling test wait <req_id>` blocks at zero tokens.
- `hauptling test report <req_id> report.json`.
- Request: `{id, from, sha, branch, selector, gpu, artifacts[], timeout_s, round}`.
- Report: `{id, sha, status: pass|fail|error|timeout, passed, failed, skipped, duration_s, failures:[{test_id, loc, message ≤300, excerpt ≤20 lines}], artifacts, log_path, notes ≤300}`.
- Reports for a different sha are rejected. Round 5 sets the agent to `blocked`, and so does every 5th round after it (see "Test-round cap").
- **GPU tests run deterministically, no LLM**, in a fresh `--gpus all` test container, one at a time on their own queue (phase 3; an earlier design used a host worktree).

### Merge gate / test jobs (2026-11-25)

- **Tests scale with the host** (2026-11-27; replaces the fixed defaults "3 CPU jobs, one per repo, one GPU job"): a test job starts when the host has room for what its repo's runs were measured to use.
  - **Measured cost**: the runner reads its container's cgroup at the end (`memory.peak`, `cpu.stat`) and puts `resources: { mem_peak_mb, cpu_s }` in the report; the broker keeps a repo's last 5 finished (pass/fail) runs, CPU and GPU jobs apart. A job counts as the highest of them plus a fifth (RAM: +128 MiB; cores: CPU seconds / wall time), never above its container's limits. A repo with no measured run counts as those limits (2560 MiB and 3 CPUs; GPU jobs 6 GB and 4).
  - **Admission**: the first job always starts. Beside running jobs, RAM: `MemAvailable`, less a margin (1 GiB or 10% of RAM) and the full estimates of jobs started under 2 min ago (they haven't claimed theirs yet), must cover the job. CPU: cores, less the higher of the 1-minute load and the running jobs' estimates, must cover it. Rechecked when a job ends and each minute. Workers' own use is in the measured free RAM and load, not modelled.
  - **Order**: oldest first; a job with no room lets smaller ones behind it start, until it has waited 5 min, then nothing starts ahead of it.
  - **GPU jobs in parallel**: also gated on VRAM. A job counts as the repo's `"gpuMemMB"` if declared, else the repo's measured peak plus a fifth and 256 MiB, else 6144 MiB. Measured by the broker: free VRAM at the job's start less the lowest seen while it ran (sampled every 5 s), only for a run that had the GPU to itself, since two jobs can't be told apart. Beside running jobs, what they are counted as but haven't claimed yet (against free VRAM before the batch) stays reserved. Waiting for our own jobs is not "GPU busy": the 30 min error clock runs only when nothing of ours holds the GPU.
  - **Limits still apply when set**: host `testConcurrency` (unset: one job per core at most), a repo's `"testConcurrency"`, host `gpuConcurrency`. `"testScaling": "fixed"` in `~/.hauptling/config.json` brings the fixed defaults back. `hauptling test scale` and `hauptling gpu status` show what is free and what each repo counts as.
  - Heuristics, not guarantees: a run that peaks late or above its measured history can still push the host into swap or a CUDA out-of-memory failure.
- **CPU jobs run in parallel** (per-repo limit 2026-11-26): up to `testConcurrency` at once host-wide (host `config.json`, default 3, was 2), and per repo at most one by default. A repo may raise its own limit with `"testConcurrency": N` (integer ≥ 1) in its `hauptling.json`; the host value stays the overall cap. The broker reads it from the job's base branch, never the agent's branch or clone, so a worker can't raise its own limit: local-path repos from the host checkout (`git show <base>:hauptling.json`), GitHub repos through the host's `gh` (contents API); a request without an agent uses the default branch. It is looked up only when a repo has more than one CPU job queued or running, and cached for 60 s; a missing, unreadable or invalid value means 1 (a failed lookup keeps the last value read). FIFO otherwise (a repo at its limit is skipped, not blocking the line). External runners (`test.claim`) follow the same per-repo limit. GPU jobs keep their single queue. Each job has its own checkout, artifacts dir and container; image builds are shared, so concurrent jobs needing the same image wait for one build (if it fails, each waiter tries from its own checkout).
- **An agent that ends gives up its tests**: kill, PR closed, failed, merged or handed off cancels all its queued and running test jobs (gate and agent requests, CPU and GPU). Running ones get their `hauptling-test-<id>` container stopped. Same path as a newer report superseding older gates: the job is marked done with status `cancelled`, never reaches the gate logic, emits no gate event; a late result is discarded. PR polling cancels outstanding jobs when it detects an external merge. At startup, queued and running jobs of killed, merged, failed, closed, handed-off or exited agents are cancelled before remaining running jobs are requeued.
- **Dashboard**: the header's GPU area shows CPU tests (running/limit, each running job's agent, repo and elapsed time, number queued). A queued job's headline gives its place in its queue ("Merge gate queued, 2nd in line"); "Running merge gate" once it runs.
- **Dashboard** (2026-11-25): each Board group heading has two icon toggle buttons after the group name, a shield-check (merge gate) and merge arrows (auto-merge); on is accent-coloured, off is muted with a slash, `aria-pressed` and a title say the state and the click action; turning the gate off asks for confirmation.
- **Refused merge** (2026-11-26): when merging a reported agent's work fails (`gh pr merge`, with or without `--auto`; or the local-repo merge), the delegator gets `[merge-failed]` with the message, the agent goes back to `working` and is mailed to rebase onto `origin/<base>`, resolve conflicts, test and report again; `hauptling merge` also fails with the message. A `gh` failure on a PR that turns out to be merged counts as merged. A local repo whose base is checked out with uncommitted changes (or that can't be read) is not the worker's to fix: `[merge-failed]` only, the agent stays `done` for a later `hauptling merge`. A conflicting local merge is aborted. pushToMain keeps reporting a failed push as `[gate-failed]`.
- **Test jobs survive a broker restart** (2026-11-26): the test container runs detached (no `--rm`); the broker waits for it, reads `report.json` from the job's artifacts dir, then removes it. On startup each `running` job is adopted if its container still runs (same hard cap, counted from the container's start; watchdog, `gpu pause --now`, cancellation and the one-GPU-job rule apply as before), collected if it has already written its report, and requeued at the front only when there is no result to recover (container gone or exited without a report, never started, or Docker not answering). Other leftover test containers are removed. Satellites run the same broker code, so the same holds there.
- **Watchdog** (2026-11-25): a locally run test job (CPU or GPU, gate or agent request) whose runner is lost is killed and rerun instead of holding its slot until `timeout_s`. Lost means: its `hauptling-test-<id>` container is gone or exited without a `report.json`, `docker run` or `docker wait` failed without one, or (container running) neither the job's `test.log` nor the runner's heartbeat (`/artifacts/heartbeat`, touched every 30 s while `hauptling test-exec` runs, so long silent tests aren't mistaken for hangs) changed for `testStallSec` (host `config.json`, default 300). Clone and image build before the container starts aren't watched. The broker checks each running job every minute (the poll). On a loss it runs `docker rm -f`, logs it once in `broker.log`, and requeues the same row (`tests.attempt` +1, `tests.retry_note` "retrying (2/3): <reason>") at the front of its repo (same `created_at`, no extra test round); a GPU job's runner is released first so the GPU queue moves on. At most `testRetries` reruns (default 2); the next loss reports the job `error` with notes "runner unresponsive (3 attempts)" through the usual path (`test wait`, gate-failed). `timeout_s` stays the hard cap: a timeout fails as before, never retried. Jobs claimed by external runners (`test.claim`) aren't watched. Dashboard: the CPU tests indicator and the agent headline show "retrying (2/3)".
- **Run now**: a queued CPU job shows a "Run now" button (card and detail); it starts the job at once, past the concurrency limit and the one-per-repo rule. POST-only dashboard action (`test.run`, like kill), admin only, queued jobs only. Not for GPU jobs: those share one GPU and use the GPU queue controls.

## Git

- **Default: own branch, PR, auto-merge when checks pass.** Push to main is a per-repo opt-in.
- Workers never touch GitHub: on `hauptling report` the host broker pushes the branch, opens the PR with your host `gh` login and enables auto-merge. Repos without required checks get a hauptling test job as the gate; the broker merges on pass.
- Local-only mode: branches, delegator merges when tests pass.

## Usage and handoff

- At **85% of the delegator's own vendor window** `wait` returns `[handoff-due]` (token economy stage 2; you can still ask earlier); it runs `hauptling handoff`, you start the next CLI and run `hauptling resume`.

## Security

- **Container egress allowlist**: containers sit on an internal Docker network with no route out; a hauptling egress proxy (domain allowlist in `~/.hauptling/egress-allow.txt`, blocked hosts logged) is the only exit: vendor APIs and sign-in, GitHub, package registries.
- **Credentials in a per-slot directory** (`~/.hauptling/slots/<slot>/`: Claude, Codex and agy config dirs) mounted into each fresh container, so containers stay signed in and fresh images never roll back rotated refresh tokens. **One container per slot per vendor** (2026-11-25): a slot can run a Claude, a Codex and an agy worker at once, so capacity is slots × vendors. This is safe because each vendor keeps its tokens in its own dir under the slot (`claude/`, `codex/` + `codex-key/`, `gemini/`), and a container mounts only its own vendor's dir(s) at `/home/worker/.vendor/<dir>`, never the whole slot. A codex worker cannot read or refresh the slot's Claude token, and two workers of the same vendor never share a slot, so no refresh token is ever held by two processes. Workers sharing a slot all run as your host uid, but each container has its own `/work` (the agent's clone in `~/.hauptling/work/<agent>`) and its own `/home/worker` (container-local), so nothing overlaps. Usage readings (`slot_usage`), sign-in locks and the Usage page's "locked" state are all keyed by slot and vendor.
- **Host-wide worker cap** `maxWorkers` (host `config.json`, default 6): live workers across every delegator, so CPU and RAM aren't overrun now that slots × vendors can exceed what the machine holds. Spawns past it queue; a delegator's own `max_agents` still applies on top.
- **GitHub**: host `gh` login does pushes, PRs and merges; workers hold no GitHub credentials. Main protected.
- **Broker**: containers reach it only through the egress proxy's relay, with per-agent tokens that cannot call kill, merge or spawn.
- No credentials in mail or on the dashboard.

## agy (Antigravity CLI) specifics

Sources: https://antigravity.google/docs/cli/headless/, https://antigravity.google/docs/cli/reference/, https://antigravity.google/docs/cli/commands/resume/

- **Auto mode**: `--mode auto` (also `accept-edits`, `plan`) or `--dangerously-skip-permissions`.
- **Resume**: `agy -c` (latest in workspace) or `agy --conversation <id>`.
- **No way to inject into a running TUI.** Mail reaches agy through its hooks (PostToolUse, Stop) while working, and `tmux send-keys` to wake it when idle.
- **Avoid headless `-p` for work**: google-antigravity/antigravity-cli#1411 measured 2.5–7× more quota per turn because each process starts with a cold cache.
- **Usage**: `/usage` (alias `/quota`) and `/credits`. No documented machine-readable form; `agy --output-format json --print /usage` works per a user report, untested. Reset time only appears in quota error text, so the panel may show it as unknown.
- **Auth**: tokens in the OS secure keyring, settings in `~/.gemini/antigravity-cli/` (both on the creds disk). Headless runs need one interactive sign-in first; the only alternative is `GEMINI_API_KEY`.
- **Claude and GPT models on the agy plan** (2026-11-27): the plan includes Claude Sonnet/Opus and GPT-OSS, counted against their own 5h and week windows ("Claude and GPT models", agy bucket ids `3p-5h`/`3p-weekly`), apart from the Gemini ones. Seen in `agy --output-format json --print /usage` on 1.5.16 (`command.data.groups[].buckets[]`).

- **Where**: GPU jobs run in a fresh test container with `--gpus all`, same image (base or per-repo) and egress rules as CPU tests. Setup installs the NVIDIA Container Toolkit. (Replaces the host-worktree design: repo code is untrusted.)
- **Host GPU runner** (2026-11-26): `"gpuRunner": "host"` in `~/.hauptling/config.json` stops the broker starting GPU containers; GPU jobs then wait for `hauptling runner --gpu`, an external runner (runner token, `test.claim` with `gpu: true`) that checks the sha out in its own work dir and runs the repo's `"gpu"` command on the host through the same `execTests`, sending `test.heartbeat` while it runs. Claims honour `gpu pause`, the VRAM wait and one GPU job at a time. Why: a container on WSL2 gets CUDA but no Vulkan, so WebGPU in Chrome falls back to software and loses the device; Windows Chrome on D3D12 works. It can run on Windows (`node.exe` on the `\\wsl.localhost` path, `HAUPTLING_BROKER` + `HAUPTLING_TOKEN` from `hauptling runner token`, passed with `WSLENV`). Repo code runs unsandboxed there, so this is for repos you trust; the watchdog and `gpu pause --now` don't reach externally claimed jobs.
- **Test progress** (2026-11-26): every running test job (CPU or GPU, gate or agent request, container or host runner) shows a bar on the dashboard: time since the claim against the typical run (median of the repo's last 5 finished runs with the same runner kind and selector; a sliding bar while there are none, amber once past it, capped short of full), plus "N done" result lines and the latest one. Where: the card's test chip, the agent detail, and the header's CPU tests and GPU details. `execTests` appends output to `test.log` as it arrives (it used to write it on exit) and keeps `progress.json` (step install/tests, latest line, result count: lab gate `ok`/`FAIL`, TAP, node:test ✔/✖) next to it; the broker reads that file for container jobs, and an external runner sends the same in `test.heartbeat { id, progress }` (on new output, at most every 5 s, else every 30 s). Progress older than the job's claim (an earlier attempt) is ignored and it is dropped on report.
- **Lease**: only GPU test jobs hold the GPU; workers reach it only through `hauptling test request --gpu`. No interactive worker lease.
- **Queues**: a GPU queue runs beside the CPU queue (one job each at a time). GPU jobs default to 6 GB RAM and 4 CPUs (`~/.hauptling/config.json`).
- **Command**: `hauptling.json` must declare `"gpu": [argv]` (same `{selector}`/`{junit}` placeholders as `"test"`); without it `--gpu` is rejected. No fallback to the test command, no auto-detection.
- **CUDA**: nothing added to `hauptling-worker`. Repos rely on wheels that bundle CUDA (PyTorch, JAX) or add it in `hauptling.Dockerfile`. `doctor` runs `nvidia-smi` in a throwaway `--gpus` container.
- **Shared desktop GPU**: before starting, the broker checks free VRAM (`nvidia-smi`) against 6 GB or the repo's `"gpuMemMB"`; if short it rechecks each minute and after 30 min reports `error: GPU busy`. `hauptling gpu pause|resume|status` holds the queue by hand. Waiting time doesn't count toward `timeout_s`.
- **Pause**: `gpu pause` lets the running job finish; `gpu pause --now` kills it and requeues it at the front without using a test round.
- **Broker restart** (both queues): superseded 2026-11-26, see "Test jobs survive a broker restart".
- **No GPU host**: setup detects `nvidia-smi`; without it the toolkit is skipped, `doctor` says "GPU: none (GPU tests disabled)" and `--gpu` fails fast with "no GPU on this host". `"gpu": false` in config disables it on a GPU host.
- **Merge gate**: CPU only by default. `"gateGpu": true` in `hauptling.json` adds the GPU command to the gate; while it waits the agent status shows `gate: waiting for GPU`.
- **Superseded gates** (2026-11-25): queuing a gate for an agent cancels its older gate jobs (other sha): `queued` ones are marked done with status `cancelled`; a `running` one is also killed via `killTestJob`, as `gpu pause --now` does. A cancelled gate never reaches `gateResult`, so it emits no `gate-passed`/`gate-failed` and merges nothing; only the gate for the agent's current sha can merge (`gateResult` still ignores a sha that isn't the agent's head).
- **Dead container** (dashboard): the `/screen` answer this covered went with the Screen tab (2026-11-25). The Terminal tab shows "No live session" for non-live states instead of opening a stream, and a stream whose captures keep failing (container gone) sends `end` after 5 errors.
- **Per-delegator merge settings** (2026-11-25): `delegators.gate` (default 1) and `delegators.automerge` (default 1); `hauptling delegator start --no-gate --no-automerge`, `hauptling delegator set --gate on|off --automerge on|off`, and "Gate on/off" / "Auto-merge on/off" buttons in the dashboard's group heading (POST-only `delegator.set`; a muted "no gate" / "manual merge" tag when off). **Gate off**: `report` queues no hauptling test job; GitHub repos merge the PR at once (with required checks: auto-merge as before, GitHub's rules apply; pushToMain: pushes), local repos merge as `hauptling merge` does; no `gate-*` events, `[merged]` as usual. Turning the gate off cancels the delegator's reported agents' queued/running gate jobs (same cancel path as superseding) and merges them; turning it on affects later reports only. **Auto-merge off**: after the gate (or the report, gate off) the broker does not merge; it emits `[ready]` and waits for `hauptling merge AGENT` or the dashboard's Merge button (`merge` now also works for GitHub PRs: needs a passing gate test unless the gate is off or GitHub's required checks gate it). Auto-merge on keeps today's behaviour, including local repos' `[gate-passed]` + manual `hauptling merge`.
- **Timeout**: GPU jobs keep the 1800 s default `timeout_s`.

### Phase 2 decisions (2026-11-21)

- **Isolation: Docker containers, not VirtualBox.** Hyper-V is on here (VirtualBox would run slowly), RAM is 16 GB, and containers run natively on Ubuntu/WSL (Docker Desktop or colima on macOS later).
- **Runtime**: Docker Engine installed by setup; started at WSL boot via `/etc/wsl.conf` (no systemd needed), `systemctl` on Ubuntu hosts. You join the `docker` group.
- **Lifecycle**: fresh container per task (`--init`, `sleep infinity`, tmux inside), removed at cleanup. Limits default to 2.5 GB RAM and 3 CPUs (`~/.hauptling/config.json`).
- **Image**: `hauptling-worker` (Ubuntu 24.04, Node 22 + pnpm and yarn via corepack, git, tmux, python3, build-essential, the three vendor CLIs, hauptling), tagged by content hash. A repo may add `hauptling.Dockerfile` (`FROM hauptling-worker`), built and cached by hash. Test jobs run in the same image.
- **Workdir**: the broker clones each task on the host into `~/.hauptling/work/<agent>` and bind-mounts it at `/work`; commits, pushes and PRs stay host-side. Containers run as your uid.
- **Slots**: a slot is a credentials directory plus the concurrency limit; the phase 1 host users (`hl-w1…`, `hl-test`) and sudoers rule are removed, their sign-ins migrated.
- **Network**: internal Docker network `hauptling-int`; the `hauptling-egress` container is the only exit (HTTPS CONNECT + plain HTTP, allowlist) and relays the broker port to the host.
- **Egress errors** (2026-11-27): a socket error ends only its own tunnel or request and logs `ERROR <host> <code>` to `egress.log`; `uncaughtException` is logged and survived as a backstop (a failed listen still exits).
- **Node behind the proxy**: containers have no DNS, and Node's built-in `fetch` (undici; corepack's first-use download and other Node tools) ignores `HTTPS_PROXY`. Every container on the internal network (workers, test jobs, sign-ins, doctor probes) gets `NODE_USE_ENV_PROXY=1` with the proxy variables (`proxyEnv()` in `src/docker.mjs`). `hauptling doctor` checks that Node `fetch('https://registry.npmjs.org/')` works from a container.
- **Package managers pre-provisioned**: the image runs `corepack enable` and prepares `pnpm@latest` and `yarn@stable` into `COREPACK_HOME=/opt/corepack` (world-writable, so a repo's pinned `packageManager` version still downloads into it, through the proxy), with `COREPACK_ENABLE_DOWNLOAD_PROMPT=0`.
- **Dependencies installed at prepare**: `hauptling prepare` (in the container, before the CLI starts) runs the clone's `install` command (`hauptling.json` or `detect.mjs`) with a 900 s timeout, logging to `.hauptling/install.log`. A failure never blocks the worker: a line at the top of its brief names the error and the command to run itself. `node_modules/` joins `.hauptling/` and `.pnpm-store/` in the clone's `.git/info/exclude` so it is never committed.

### Phase 1 decisions

- **Code**: plain ESM `.mjs`, JSDoc, `node:test`, no build. Install: clone, then `install.sh` (Linux) or `install.cmd` (Windows, hands over to `install.sh` in WSL).
- **Broker**: sole owner of the SQLite store, auto-spawned detached by any `hauptling` command (`hauptling broker start|stop|restart|status`), listening on 127.0.0.1. Workers' `hauptling` is an HTTP client with per-agent tokens. The broker acts as worker users through a sudoers rule limited to them. (An earlier design ran the broker on Windows with an SSH tunnel into WSL; dropped as brittle.)
- **Slots**: one Linux user per slot (`hl-w1`…), 3 per delegator by default (`hauptling setup --slots N`), plus `hl-test` for test jobs. Each slot signs in to each vendor once (`hauptling login <slot> <vendor>`). Hooks are user-level in each slot; target repos are never modified.
- **Spawn**: `hauptling spawn --brief brief.md [--vendor] [--model] [--repo] [--base] [--test-writer]` clones into the slot's home, makes the branch, starts the TUI in tmux and sends "Read your brief: <path>". The worker ends with `hauptling report "<≤300 chars>"`.
- **Delegator**: `hauptling wait` blocks (zero tokens) and returns the next event (report, blocked, test result, merged, failure).
- **After done** (revised 2026-11-26): the worker is parked (see "Parking" under Phase 4 decisions) until its PR merges; then its clone and saved session are deleted.
- **Tests**: `hauptling.json` in a target repo is optional; commands are auto-detected (`hauptling init` writes the detected config). Commands are argv arrays; results come from JUnit XML. Jobs run as `hl-test`.
- **models.json**: shipped default in the repo, `~/.hauptling/models.json` overrides; round-robin state in SQLite.
- **Test writer** (`--test-writer`): tests first. A test writer (cheapest model of the next vendor by default) writes spec tests from the brief alone on the task branch and reports (`[tests-ready]`); the implementer then starts from those commits and must not weaken them.
- **Stuck workers**: once a minute the broker checks each worker. A dead TUI → `exited` (event to the delegator). No hook activity for 10 min while not idle → `blocked` and one notification (says so when a vendor permission prompt is on screen); activity resumes → `working`.
- **pushToMain** (`hauptling.json`, GitHub repos): no PR; after the gate test passes the broker rebases onto base and pushes.
- **Vendor autonomy**: Claude `--permission-mode auto`; Codex `--sandbox danger-full-access --ask-for-approval never` inside the container (phase 2: the container is the sandbox, bubblewrap can't run in Docker; phase 1 used `workspace-write` + network). `report`/`test request` commit leftover changes for any worker; agy `--mode auto --dangerously-skip-permissions`, with `toolPermission: "always-proceed"` and `enableTerminalSandbox: false` written to the worker's agy settings (2026-11-27; before: `--mode auto` with only `command(hauptling)` pre-approved). Reason: workers stalled on agy's prompts. Auto mode approves only what it judges safe, and agy's terminal sandbox failed inside Docker, so workers tried to bypass it and agy's monitor stopped to ask. The container and the egress allowlist are the sandbox, as for Codex; agy's own command denylist still applies under the flag (its changelog). Setting names are from agy 1.5.16's binary, not yet seen to take effect. Workers run `hauptling report` as a command on its own.
- **Paths**: clones live on the Linux filesystem; hauptling on PATH links to the checkout; containers get their own copy baked into the image (`hauptling image` rebuilds when it changes). Local-only repos merge via `hauptling merge` after the test job passes.

## CodeGraph in workers (2026-11-25)

[CodeGraph](https://github.com/colbymchenry/codegraph) (local code graph, MCP tools `codegraph_explore`, `codegraph_node`) in every worker.

- **One index per repo, built by the broker**: a cache on the host (`~/.hauptling/codegraph/<repo>/`), built in full the first time a repo gets a worker, `codegraph sync`ed before each spawn. The index stores repo-relative paths and per-file content hashes, so a copy works in any clone: the broker copies it into the worker's clone at spawn and the worker's prepare runs `codegraph sync` (incremental; ~1 s measured on this repo). Not the delegator's job (mechanical), and never the user's checkout (`.codegraph-wsl/` there is the user's own).
- **On by default**; `"codegraph": false` in `hauptling.json` skips it for a repo (e.g. one too large to index).
- **Image**: the CLI is installed in the worker image with telemetry off (`CODEGRAPH_TELEMETRY=0`, and `--no-telemetry` on the server; it is on by default upstream). The cache is synced by the worker's own CLI before the agent starts and saved back from the clone, so the index format always matches the image and the host needs no install. Clones are on the container's Linux filesystem, so the server's live watcher keeps the index fresh while the worker edits.
- **Use**: MCP server instructions reach only the top-level session; a worker's own subagents (Explore etc.) don't get them and fall back to grep. So the instructions appended to every brief gain one line when CodeGraph is on: use `codegraph_explore`/`codegraph_node` to find code, and tell any subagent you start to use them too. Works for every vendor.
- **Repo MCP servers**: workers load only Hauptling's MCP servers (CodeGraph) by default, like hooks: a repo's `.mcp.json` usually points at host paths, and in a fresh clone it prompts for approval. `"mcp": ["name", …]` in `hauptling.json` allowlists repo servers known to work in a container.
- **Wiring, Claude**: `/etc/claude-code/managed-mcp.json`, which takes exclusive control: Claude loads only the servers it lists and ignores the repo's `.mcp.json` (no prompt; `claude mcp add` and `--mcp-config` are refused). The broker writes it per agent at spawn (CodeGraph, plus the repo servers named in `"mcp"`, their definitions copied from the repo's `.mcp.json`) and mounts it read-only into the agent's container, which is created per agent. Not baked into the image, since it differs per repo. Verified in a worker container (2026-11-25): no approval prompt, `claude mcp list` shows only CodeGraph (Connected), a repo `.mcp.json` server is ignored.
- **Codex and agy**: use the CLI (`codegraph explore`, `codegraph node` print what the MCP tools return), named in the brief line. No MCP wiring for them yet; whether either can exclude a repo's own MCP servers is still to check.
### Token economy decisions (2026-11-25)

Goal: subscription usage windows last longer. Workers first, then the delegator; hauptling's own mechanisms only (no conventions imposed on target repos). Measure alongside the first fixes.

- **Stage 1** (measurement + cheap fixes):
  - **Per-task totals**: at launch the agent stores its vendor's window readings (`usage_start`); its final tokens are already kept. The `[report]` event and the dashboard's agent detail add one line: tokens in/out, cost, how many points each window rose during the task (a window that reset mid-task shows no delta), test rounds used.
  - **Worker preamble**: `prompts/worker-rules.md`, put in front of every brief by the broker: read files in ranges, search before reading, keep command output short (`| tail`, `-q`), run only the tests touched, reports stay ≤300 chars.
  - **Bare worker CLI**: workers load no user MCP servers or plugins, only hauptling's hooks. Claude: the per-agent `managed-mcp.json` (see "CodeGraph in workers"; it already admits only Hauptling's servers, so the branch's `--strict-mcp-config` was dropped in the 2026-11-25 merge, as it could shut CodeGraph out) and every `enabledPlugins` entry set false in the slot's settings; hooks and status line stay managed in the image (see Workers). Codex: `-c mcp_servers={}` in its launch template. agy: unknown, open.
  - **Test-round cap** (2026-11-27; was round 3 and every round after it): round 5 blocks the worker with a question to the user ("Keep iterating?"); after "Keep going" it asks again only every 5 rounds (10, 15, …). The interval is `TEST_ROUND_ASK = 5`, overridable as `testRoundAsk` in host `~/.hauptling/config.json`.
  - **Cheaper-model preference**: `"prefer": "cheap" | "balanced" | "best"` in `~/.hauptling/models.json` (shipped default `best`, i.e. no change) caps the tier spawn may use at 1, 2 or 3. A model above the cap is refused unless the spawn passes `--allow-tier`; `--mode rule` clamps to the cap; `cheapest` and test writers are unaffected. Set with `hauptling models prefer <value>` or the Usage tab's toggle; `hauptling models` prints it first so suggest mode reasons with it.
- **Stage 2**:
  - **Effort per tier**: `models.json` `effort` per tier (1 low, 2 medium, 3 high), passed through each vendor's `effortArgs` (Claude `--effort`, Codex `-c model_reasoning_effort="…"`; agy has none: its model ids carry it, and `--effort` for agy is refused). Precedence: `spawn --effort`, the model entry's `effort`, the tier default. Test writers get their model's default.
  - **Events-only wait (Claude delegators only)**: `hauptling wait --until-event` loops broker waits inside the CLI process until an event arrives; the skill runs it as a background command and Claude Code wakes on its exit; no empty-timeout turns. Codex and agy keep the ~4.5 min loop.
  - **Auto handoff**: at 85% of a window of the vendor the delegator's CLI runs on (`delegators.cli`), active delegators get one `[handoff-due]` event per window; the delegator writes the note. Readings come from the delegator's own CLI: `hauptling setup` points the host's Claude and agy status lines at `hauptling usage <vendor> --host` (the previous status-line command is kept in `~/.hauptling/statusline-prev.json` and chained, so its output still shows); a Codex delegator's windows come from the host's `~/.codex` session log. Host readings live in `host_usage`, apart from the slots' (the host may use another account) and don't affect routing. Until the host has reported for a vendor, slot readings of that vendor stand in (same-account assumption).
- **Stage 3** (built 2026-11-26): **headroom-aware round robin**: skip vendors at ≥80% of any window (a reading whose `resets_at` has passed counts as free). All vendors ≥80%: new spawns stay queued with one notification; running workers continue.
  - **Headroom**: a vendor lacks it when, for any window, the newest `slot_usage` reading from any slot is ≥80% and its `resets_at` is unknown or ahead. No reading, or an `api`-billed spawn: headroom. Threshold `HEADROOM_PCT`, overridable as `headroomPct` in `~/.hauptling/config.json`. The 100% rule reads the same newest readings, so a stale one from another slot no longer holds a vendor.
  - **Automatic vendors**: a spawn without `--vendor` or `--model` (also a test writer without either) rotates past vendors lacking headroom, and the agent remembers its pick options (`agents.auto`). While it is queued, if its vendor lacks headroom, it moves to the next vendor that has headroom and a free slot: vendor, model and effort change, and **the agent is renamed** (below). Once started, an agent keeps its vendor and id (restart, unpark: never gated).
  - **Rename on a switch** (user, 2026-11-27; replaces "keeps its id"): a queued agent that switches vendor or model gets a new `<vendor>_<model>_<hex>` id and the branch `hl/<new id>`; its row, mailbox, events, asks, test jobs, per-agent kv keys and other agents' `depends_on` follow in the same transaction, and the delegator gets `[renamed] <old> → <new> (headroom: …)`. The old id (or its hex key) stays an alias (`aliases` table) for the agent's life: CLI commands accept it and say so, mail to it arrives, the dashboard follows it. Only on the hub, before placement, so a satellite only ever sees the final id. A test writer's branch is the implementer's task branch, so it keeps that name. An implementer renamed after its spec tests were pushed starts from them (`start_from`) on its new branch; the old branch stays on the remote.
  - **Explicit** `--vendor`, or a `--model` that belongs to one vendor (which now implies it): queued only at 100%, as before; the spawn output warns at ≥80%.
  - **All lack headroom** (every enabled vendor that isn't out of credit): the spawn is accepted and stays `queued`; each delegator with such a spawn gets one `[headroom]` event, and you get one notification, per stretch. Both name the vendors with their fullest window and the earliest time one regains headroom. The stretch ends when any vendor has headroom again; the poll then starts the queue in order. `status` and the dashboard headline say "waiting for headroom (…)".
  - Hub only: satellites' readings aren't used, and satellite placement isn't gated.

## API keys (optional)

- `hauptling key set <vendor>` (key from stdin or a hidden prompt, never argv) stores one key in `~/.hauptling/keys/<vendor>` (600). It switches that vendor to API billing for **every** slot: keys don't rotate, so one key serves all slots and no per-slot sign-in is needed. `hauptling key rm <vendor>` switches back to the slots' sign-ins. Running workers keep what they started with.
- Claude: `ANTHROPIC_API_KEY`, pre-approved in the slot's `.claude.json` (`customApiKeyResponses`), onboarding marked done. Codex: `OPENAI_API_KEY` stored by `codex login --with-api-key` in a separate `CODEX_HOME` (`<slot>/codex-key`) so the slot's ChatGPT sign-in stays intact. agy: `GEMINI_API_KEY` (untested here which wins when an OAuth sign-in is also present).
- The usage page and `doctor` show "API key …abcd" for that vendor instead of per-slot sign-ins.
- **Monthly API budget (API first, then the plan)** (2026-11-25): `hauptling key budget <vendor> <usd> [--resets-on DAY]` (or `key set <vendor> --budget <usd>`) gives the key a monthly budget, e.g. free API credits. The key then no longer covers every slot: each spawn takes the API while this period's API spend is under **90%** of the budget, else the slots' sign-ins (which must stay signed in). Running API workers finish on the API; the 10% margin covers them, so spend rarely passes the budget. A worker can't switch billing mid-session, so they are never restarted. `key budget <vendor> off` returns to key-for-every-slot; `key rm` drops key and budget.
- Each agent records its billing (`api` or `plan`) at start. Period spend = sum of the reported cost of this vendor's `api` agents created since the last reset day (default the 1st, local time). Hauptling's own tally: an ordinary API key can't read the credit balance, and spend outside Hauptling isn't counted. An API spawn ignores the plan's 5h/week limits; a plan spawn waits for them as before.
- At 90% one notification and an `api-budget` event to the delegator, once per period. The header shows an "API $63/$100" chip, the vendor card the same plus the reset date; spawn output and agent rows say `api` or `plan`.
- **Spend survives restarts** (2026-11-26): `agents.usage` holds totals across CLI sessions (`session` = the current one, `base` = the finished ones folded in). A new session is a changed `session_id` or a lower reported cost; for Codex also lower token totals (its log counts cumulatively). Claude's token counts are the current context, so a drop there alone means nothing; its tokens add up one last reading per session. Within a session an estimate never goes down.
- **No free API work**: for an `api` agent a reported cost of 0 (or none) with tokens > 0 is replaced by the models.json estimate, marked estimated. For Claude that prices only the current context, so it is a floor.
- **Out of credit**: each minute the watcher looks for the vendor's billing error on an `api` worker's screen (at the start of a line, so quoted text doesn't count; patterns in `OUT_OF_CREDIT`, `src/usage.mjs`). The agent goes `blocked: API credit ran out`, the delegator gets `api-exhausted` once per agent (kill and respawn: it can't switch billing, and `kill` deletes its working tree, so save the work first), and the key is marked exhausted with one notification. With a budget, new spawns use the slots' sign-ins until the period resets; without one, spawns of that vendor are refused (queued ones wait). `key set`, `key budget` and `key rm` clear it. A worker started before the current key was set doesn't mark that key.
- **Model-tier ceiling** (user, 2026-11-27): the key pays only for models up to a tier (e.g. sonnet and below, not opus and above). `hauptling key set <vendor> --up-to <tier|model>`, `hauptling key budget <vendor> <usd> --up-to …`, and `hauptling key up-to <vendor> <tier|model|off>` to change it alone. The value is a tier (1–3) or a model name (`sonnet`, `sonnet-5-5`, `opus`) resolved to its tier through models.json; an unknown name, or one matching several tiers, is refused before anything is stored. Stored per key (`<vendor>.upto`); `off` = no ceiling; `key rm` drops it, re-setting the key or budget keeps it.
  - A spawn (test writers by their own model) whose model's tier is above the ceiling is billed `plan`, never `api`, whatever the budget; a model missing from models.json counts as above. At or below it the rules above apply. Running workers, and restarts of them, keep their billing.
  - This also holds for a key without a budget, so the slots must stay signed in: `key set`, `key up-to`, `setup` and `doctor` say which aren't. An above-ceiling worker only starts on a signed-in slot. A key out of credit doesn't refuse above-ceiling spawns (they don't use it).
  - If the plan can't take it (no free signed-in slot's sign-in, 100% of a window, or for a rotation-chosen vendor the headroom threshold), it stays queued, headline "waiting for plan (opus above API ceiling sonnet)"; it never falls back to the API. A rotation-chosen vendor may still move to another vendor as in "Headroom".
  - Model selection is unchanged (`--mode cheapest|rule` and suggest don't steer toward the ceiling). Spawn output says `api` or `plan`, with `(above API ceiling)` when the ceiling caused the plan. `key list`, the vendor card and the header API chip show "up to sonnet (tier 2)".
  - Each host applies its own keys and ceilings; a satellite's "waiting for plan" headline is not mirrored to the hub.

## Several hosts (2026-11-25)

Built in three parts: 1 = this design, the store and the hub/satellite link; 2 = spawning, tests and GitHub on satellites, placement; 3 = dashboard.

- **Hub and satellites.** This machine's broker is the **hub**: delegators, the store, the dashboard, the event stream and `wait` stay there. A **satellite** is a broker on another host that only runs workers and test jobs on its own slots, signed in with its own vendor accounts. Credentials never move between hosts (Claude refresh tokens rotate, so copies would sign each other out). With no satellites the hub works exactly as before.
- **Link.** Satellites connect **out** to the hub over Tailscale (the hub URL is a tailnet address, e.g. the `tailscale serve` HTTPS name in front of the broker port) and keep one authenticated, long-lived connection: SSE from the hub for commands, POST for state and events back. No inbound port on satellites. The satellite refuses a hub URL that is plain `http` unless it is loopback or a tailnet address (`100.64.0.0/10`, `*.ts.net`), so the key never crosses an untrusted network in clear.
- **Joining.** `hauptling hub token` on the hub prints a one-time join token (`hlj_…`, expires in 15 min; only its SHA-256 is stored). `hauptling satellite join <hub-url> <token> [--name H]` on the other host exchanges it for a revocable per-satellite key (`hls_…`; the hub stores only its SHA-256), saved in `~/.hauptling/satellite.json` (600, dir 700, like `broker.json` and the API keys); then `hauptling broker restart` makes the broker dial out. The name defaults to the host name (lowercase `[a-z0-9.-]`, not `hub`). Re-joining under an existing name replaces its key (the old one stops working) and starts its event numbering over. `hauptling satellite list|revoke <host>` on the hub; revoking drops the key and closes the open link at once.
- **Scope.** A satellite key can only act for its own host's agents and tests: on `/api/*` it is role `satellite` and every call outside its (part 2) list is refused, so no delegator, admin, DB or other-host calls; events it sends for an agent on another host are dropped. Every satellite request is logged with the host (`broker.log`, `hub <host> …`).
- **GitHub.** A satellite pushes branches, opens PRs and merges with **its own** `gh` login, as the hub does today. Only **GitHub repos** can run on satellites; local path repos stay on the hub. (Part 2.)
- **Tests.** A satellite's workers use **that host's** test queue and GPU queue; the hub only shows them. (Part 2.)
- **Placement.** `delegator start --host H` or `delegator set --host H` binds a delegator to a host. Unbound delegators auto-place: a host with a free slot signed in to the vendor (GPU tasks to GPU hosts), least busy first. `spawn --host H` overrides either. `hub` names this machine. (Part 2.)
- **Offline.** If a satellite drops, its agents show "host offline" on the board and in `status`. Nothing is killed. The satellite queues its events while offline and replays them, in order and de-duplicated by id, when it reconnects. After 24 h offline each delegator with live agents on it gets one `[host-lost]` event (again only after the host has been back and drops again).

### Store

- `hosts`: `name`, `key_hash`, `created_at`, `last_seen`, `online`, `offline_since`, `lost_at`, `capabilities` (JSON: vendors → signed-in slots, `gpu`, `free` slots per vendor, `maxWorkers`), `last_seq` (highest event id taken from it). `join_tokens`: `hash`, `expires_at`, `used_at`.
- `agents.host` and `tests.host`, default `hub`.
- On a satellite, `outbox` (`seq` AUTOINCREMENT, so ids are never reused) holds events not yet acknowledged by the hub.
- Part 2: `delegators.host` (NULL = auto), `agents.want_host` (a `spawn --host` pin), `agents.gpu` (`spawn --gpu`), `asks.remote_id` (the satellite's question id), and on the hub `commands` (`id` AUTOINCREMENT, `host`, `type`, `body` JSON, `created_at`, `acked_at`, `result`).

### Protocol (all on the broker port, under `/hub/`)

- **Auth header:** `Authorization: Bearer hls_…` plus `X-Hauptling-Host: <name>`; both must match a non-revoked host, else 401 (the satellite then stops dialling and logs "key revoked; join again").
- `POST /hub/join` `{host, token}` → `{host, key}`. No auth header; the join token is single-use and refused once used or expired.
- `GET /hub/link` → `text/event-stream`, held open. Messages: `hello` `{host, acked}` (the last event id the hub holds), `command` `{id, type, …}` (part 2: spawn, kill, …), `revoked` (then the stream ends), and a `: ping` comment every 15 s to keep proxies from idling it out. Opening the link counts as a heartbeat. A second link from the same host replaces the first.
- `POST /hub/state` `{capabilities}` → `{acked}`. Sent on connect and every 30 s: it is the heartbeat. The hub marks a host online on any authenticated request and offline after 90 s without one (checked every 30 s).
- `POST /hub/events` `{events: [{id, agent, kind, text, at}]}` → `{acked}`. Ids increase per satellite. The hub takes events in id order, skips any id ≤ `last_seq` (a replay), raises `last_seq` in the same transaction as the insert, and answers the new `last_seq`; the satellite deletes its outbox up to `acked`. So a lost answer just means a replay that the hub skips: exactly once, in order.
- **Reconnect:** on a failed request or a closed stream the satellite retries the link with backoff 1 s, doubling to 60 s, ±20% jitter; it resets after a successful connect. Events raised meanwhile wait in `outbox`; on reconnect it sends its state, then replays the outbox in batches of 100.

### Part 2: running work on satellites (2026-11-26)

- **Placement.** `delegators.host` (NULL = unbound) is set by `delegator start|set --host H` (`--host auto` unbinds); `spawn --host H` pins one agent (`agents.want_host`). A queued agent goes to its pin, else its delegator's host, else auto: every host that fits, least busy (fewest live workers) first, the hub on a tie. A host fits when it is online (the hub always is), has a slot signed in to the vendor with no live worker of that vendor, is under its `maxWorkers`, and, for `spawn --gpu` tasks, has a GPU. The hub's slots and limits are its own; a satellite's come from its last `capabilities` (signed-in slots per vendor, `maxWorkers`, `gpu`) minus the agents the hub has placed on it that are still live. The delegator's `max` counts agents on every host. If nothing fits the agent stays queued; `startQueued` runs again on every `poll`, and whenever a satellite sends state or ends an agent. `--host` must name `hub` or a joined satellite; a local path repo on a satellite is refused (`local repos run on the hub only`).
- **Commands.** Placing an agent on a satellite, and every action on an agent whose `agents.host` is not `hub`, become a `command` on `/hub/link` instead of running locally. Types: `spawn` (the agent row and its delegator's `gate`/`automerge`), `kill`, `pause`, `resume`, `restart`, `merge`, `reply` (free text from you), `answer` (to the satellite's own question id), `mail` (mail to a worker there), `test-run` (run a queued job now), `delegator` (gate/automerge changed). `attach` relays the terminal through the hub (part 3).
- **Exactly once.** Commands are stored on the hub (`commands`: `id` AUTOINCREMENT, `host`, `type`, `body`, `acked_at`) before sending, and every unacknowledged one is sent again, in id order, whenever the link opens. The satellite records the highest command id it has started (`kv`) and skips ids at or below it; it answers each with an outbox event `cmd` `{id, ok, result|error}`, which rides the exactly-once outbox. The hub acknowledges a command when that event arrives. Commands for one agent run in order; different agents' commands run concurrently.
- **Answers to the caller.** With the link open the hub waits up to 30 s for the `cmd` event and answers with the satellite's result or error. With the satellite offline the call answers at once with `queued: true` and "host offline; delivered when it reconnects". `kill` of an agent on an offline host also marks the hub's row killed at once, so the delegator's limit frees; the satellite stops the worker when it reconnects.
- **Satellite side.** The satellite keeps its own rows: a copy of the hub delegator (inactive, its gate/automerge) and the agent (its own worker token), and runs the usual code (clone, container, prepare, report, gate, PR and merge with its own `gh`, its own test and GPU queues, `poll`, `watch`). It never reads the hub's DB. Every delegator event it raises for an agent goes to the outbox instead of its own events table, plus mirror kinds: `state` (the changed agent columns and its status line), `test` (a test job row), `ask` (a question, with the satellite's id), `notify` (a stall, idle or usage notification, shown by the hub instead of on the satellite). Mail from a worker there to an identity the satellite does not know goes up as `mail`. Mirror payloads may be up to 64 KB; other event texts stay at 600 characters; a flush batch stops at 100 events or 512 KB.
- **Hub mirror.** The hub applies `state` and `test` to its rows (with that host), turns `ask` into its own question (`asks.remote_id`; notification and answer page as usual), delivers `mail`, and records the rest as delegator events, so `wait`, `status` and the board see them as if local. `tests-ready` also releases the waiting implementer (placed anywhere, since the spec tests are on GitHub). A `state` never revives an agent the hub already ended (killed while its host was offline); events for agents on another host are dropped. The hub never runs a satellite's agents or jobs itself: its slot counts, watch, PR poll, usage reading, test queues and restart recovery only look at `host = 'hub'`.
- **`/api/*` for satellite keys:** none. Everything a satellite tells the hub goes through `/hub/state` and `/hub/events`, so it is ordered and exactly once; every `/api` call with a satellite key is refused.
- **`status`** shows a host column when any satellite is joined, and `host offline` for agents on a host that is.

### Part 3: dashboard and terminal through the hub (2026-11-26)

With no row in `hosts` the dashboard (board snapshot, usage, pages) is exactly as before; everything below appears only once a satellite has joined (revoked ones included, since their agents may still be on the board).

- **Board.** Each agent card and the detail pane carry a small muted host chip (`hub` or the satellite's name). An agent in a live state (queued … done) on a host that is offline gets `host_state: offline`: headline "Host offline: <host>", a grey dot and "host offline" instead of its state in the detail meta, never "working". After the hub raised `[host-lost]` (`hosts.lost_at` set) it says "Host lost: <host> (offline over 24 h)". Kill, pause, resume, restart, run now and reply stay usable: they become commands as in part 2, the toast says "will run when <host> reconnects", and the detail pane shows that hint under the buttons. "Enable input" is the hub's own switch, so it works offline too; keys typed while the host is offline are refused (not queued: nobody can see what they would hit).
- **Hosts panel.** On the Usage page, a collapsible "Hosts" panel (a `<details>`, open by default) under Accounts: per host online/offline/revoked, last seen, signed-in slots per vendor, free slots per vendor, GPU, live workers vs `maxWorkers`, pending commands. "Revoke" asks to confirm, then does what `hauptling satellite revoke` does. "Add host" issues a join token (`POST /dash/hosts/token`) and shows the line `hauptling satellite join <hub-url> <token>` with a copy button and its expiry (15 min). The hub URL is the address the browser used when that is not loopback (the `tailscale serve` name, from `X-Forwarded-Host`/`Host`), else the placeholder `<hub-url>` with a note to use the tailnet URL. The first satellite still joins with `hauptling hub token` (no panel without satellites). A joined satellite's own dashboard has none of this (it gets no `hub`; `/dash/hosts/token` there answers "add hosts on the hub"). The dashboard's usual guards apply (127.0.0.1 only, the dashboard cookie, `X-Hauptling` on POSTs), so a satellite key never reaches these routes; on `/api` it is refused as in part 2.
- **RPC over the link.** For things that need an answer now and must not be replayed (terminal frames and keys, diff, the satellite's half of the timeline) the hub sends `rpc` `{req, op, …}` on `/hub/link`, not stored; the satellite answers `POST /hub/reply` `{req, ok, result|error}` with its key (a reply for another host's request is dropped). Ops: `term.screen` `{agent, since}` → `{text, hash, alive}` or `{same: true, alive}` when the screen's SHA-1 equals `since`; `term.keys` `{agent, keys}`; `term.resize` `{agent, size}` (`{cols, rows}`, or null to restore); `diff` `{agent}`; `timeline` `{agent}`. The satellite runs at most 16 at once and answers only for agents it has (never a login session). A reply is at most 4 MB (a diff is cut to fit and says so). The hub waits 20 s; a link that closes fails its open requests with "<host> is offline". With the host offline an op fails at once.
- **Web terminal through the hub.** The hub's terminal stream for a satellite agent polls `term.screen` every 250 ms, one request at a time, passing the last screen's hash so an unchanged screen costs a few bytes; it relays at most 32 MB per stream, then ends with "relay limit reached; reopen the terminal", skips a poll while the browser's socket has over 1 MB unsent, and stops polling the moment the browser closes the stream (no satellite state to clean up). Input: the hub keeps the 10-minute input switch; keys go as `term.keys`, which the satellite sends to the worker's tmux. With the host offline the terminal shows "<host> is offline; waiting for it to reconnect" and resumes when it does.
- **`hauptling attach` on the hub** for a satellite agent no longer refuses: `attach` answers `{remote: host}` and the CLI runs the same relay over `/api/term.screen` and `/api/term.keys` (admin only): it redraws the screen on change and sends your keystrokes (raw mode; arrows, Home/End, PgUp/PgDn, Ctrl-letters); Ctrl-] detaches.
- **Diff and Events.** The Diff pane of a satellite agent is computed on the satellite (`diff`). The Events pane merges the hub's timeline with the satellite's mail for that agent (`timeline`; mail the hub already holds is not shown twice); offline, it shows the hub's part and says the rest is on the host.
- **Usage.** A satellite adds its newest reading per vendor and window (`slot_usage`) to its `capabilities` (`usage`). The Usage page shows them under each vendor card per host, and the header gets one chip per vendor and satellite, labelled `vendor@host`. Placement's `startable` still only knows the hub's own accounts (open).
- **Preview.** `node scripts/dash-preview.mjs --hosts` serves the dashboard with two fake satellites (one offline); `--only <view>-<W>x<H>` takes one screenshot.

## Turnkey deployment (goal)

After phase 1–4 work, standing up Hauptling on a **new host is one command**: clone, run the installer, sign in when asked, `doctor` passes. Hosts may be **Windows, Ubuntu or macOS**; only Windows is available for testing now.

Hosts are Linux; Windows runs everything in WSL. Platform-specific code sits behind `src/platform/` (one adapter, `linux`):

| Seam | Linux / WSL (done) | macOS (planned) |
|---|---|---|
| Installer | `install.sh` (`install.cmd` on Windows → WSL) | `install.sh` with Homebrew |
| Worker host | Docker Engine containers | Docker Desktop or colima |
| Notifications | Windows toast via interop on WSL, `notify-send` otherwise; both link to the answer page | `osascript` + answer page |

macOS stays untested until a Mac is available.

## Claude CLI mod (2026-11-28)

Dashboard controls inside the Claude Code CLI: a Claude Code mod (plugin with a hooks module) that shows the delegator's agents above the prompt and drives them without a browser. Not built yet.

- **Home:** `claude-mod/` in this repo, next to the API it depends on. `hauptling setup` installs it into the host's Claude plugins, so both a Windows and a WSL Claude get it.
- **Connection:** the dashboard API on `127.0.0.1:47800` (WSL forwards localhost, and the loopback check passes from Windows). It signs in by sending the dashboard token as the `hl_dash` cookie, read once via `hauptling dashboard --print`. POSTs carry `X-Hauptling: 1`. Live data comes from `/dash/stream` (SSE board snapshots), actions from `/dash/do/<call>`, queue moves from `/dash/agents/<id>/move`, the terminal from `/dash/term/<id>/stream|input|keys|size`, and diff and events from `/dash/agent/<id>/diff|events`. No new broker routes.
- **Activation:** the band shows while the board has an active delegator whose `repo` matches the session's `git remote` (`owner/name`). It hides when that delegator ends or the broker can't be reached. Several active delegators for one repo: one tab each.
- **Placement:** a one-row **band above the prompt**, always on while active, plus a **side pane** opened on demand (Enter on an agent, or `/h`) holding the full table, controls, terminal, diff and events.
- **Columns:** short name | model | ctx % | status circle. When the row runs out of room it collapses to circle plus initials (`● cv`). There is no progress %.
  - **Short name:** vendor plus the first distinctive word of the title, skipping prefixes like `Scenes:` and `Fix:` (`claude·vaporwave`). The 5-char ID suffix is appended only when two names clash. Initials in the collapsed form.
  - **ctx %:** `usage.context_pct`, already on the board from the workers' status lines (Claude and Codex). Shows `—` where it's missing. Open: whether agy workers report it, and if not, whether Hauptling should read it from agy's session log against the model's window in `models.json`.
- **Which agents:** queued, running, blocked, paused and in the gate, plus anything finished in the last 30 min. The pane has a "show all" toggle.
- **Status circles:** ● green running, ◐ yellow idle, ●! red blocked or asking (blinks), ‖ grey paused, ◌ dim queued, ◆ blue in the gate, ✓ merged, ✗ killed or failed.
- **Navigation:** a mod only gets keys once its site has focus. Ctrl+x tab (or the user's chord) focuses the band, ←/→ or 1–9 selects an agent, Enter opens it in the pane, Esc goes back to the prompt.
  - **Pane keys:** k kill, p pause/unpause, r restart, m merge, a answer an ask, s / S suggest, t terminal, d diff, e events, shift+↑/↓ queue move (top/bottom too).
  - **Slash commands** do the same from the prompt without a focus change: `/h kill cv`, `/h pause 2`, `/h reply cv <text>`, `/h gate off` and so on. Agents are named by short name, initials or list number.
- **Confirmation:** kill, restart and merge ask y/n inline; pressing the same key twice skips the question. Everything else acts at once.
- **Terminal:** in the pane, a live view of the worker's tmux screen from the broker's term stream, sized to the pane (the same size lease as the web terminal). Ctrl+x i turns input on and keys go through `term/<id>/keys`; the broker's 10-minute idle-off applies. Esc returns focus. No pop-out.
- **Suggest:** `s` sends typed text straight to the worker (`reply`). When the worker has an open ask, the same key shows its choices and answers it. `S` hands the text to this Claude session as a prompt ("suggest to <agent>: …") so the delegator adds context and sends the reply itself.
- **Extras (dashboard parity):**
  - Toasts plus the red circle for asks, blocks, reports and failed gates.
  - Answering asks from the pane; diff and event views; merge; the PR link.
  - Queue reorder; delegator settings (gate, automerge, host); model tier preference.
  - A pane header line with the gate and test queue, GPU pause/resume, and each vendor's 5h and weekly usage %.
- **Build and test:** `claude plugin validate`, `claude plugin test` and `tsc` against the mod's types, then a live load into a delegator session against a real broker.

## Open

- **agy session on unpark**: where agy keeps conversations (and whether `agy --conversation <id>` resumes one copied into another slot) is unknown, so a parked agy worker unparks fresh (PRD "Parking").
- Refresh token rotation (a refresh returns a new refresh token and invalidates the old one, so a second copy of a credential file gets silently signed out):
  - **Claude: yes** (reported 2026-11-24, not yet observed on a slot). Refreshes on a 401 and proactively up to 5 min before expiry; reusing an old refresh token fails with `invalid_grant`.
  - **Codex: yes** (reported 2026-11-24, not yet observed on a slot). Refreshing `auth.json` spends the old refresh token; a process or copy still holding it fails and needs a new sign-in. Restoring an old `auth.json` (backup, re-copy) has the same effect.
  - **agy: own Google sign-in unknown** (assumed yes). Its MCP OAuth tokens (`mcp_oauth_tokens.json`) do rotate, and concurrent agy processes sharing them collide: one rotates, the other reuses the old token, gets `invalid_grant`, and the file is cleared (reported 2026-11-24, from an Antigravity CLI issue).
  - Superseded 2026-11-27 by "Shared sign-ins" (one sign-in per vendor by default). Original design consequences: each slot signs in on its own; credentials are never copied between slots; the slot dir is mounted, not copied, into containers so a refresh writes back to the one real file; one worker per slot per vendor at a time, mounting only that vendor's dir. Not yet guarded: a "Sign in again" on a slot whose worker is running (two processes refreshing one file).
